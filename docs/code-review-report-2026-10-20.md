# 코드 검토 보고서

- 검토일: 2026-10-20
- 범위: `frontend/`, `app/`
- 방식: 코드 읽기 검토. 프론트엔드와 백엔드를 각각 독립 검토했습니다.
- 검증: 테스트는 실행하지 않았습니다. 이번 작업은 코드 수정이 아니라 보고서 작성이며, 기능 동작 여부를 테스트로 확인하지 않았습니다.

## 요약

우선 대응이 필요한 부분은 백엔드 계정 보안입니다. 현재 비밀번호가 평문으로 저장·비교되고, JWT 서명 키에 예측 가능한 기본값이 있으며, 키를 로그로 출력합니다. 프론트엔드는 게시글 상세 화면의 오래된 응답 반영 가능성과 글쓰기 폼의 브라우저 기본 입력 검증 누락을 확인했습니다.

## 백엔드 (`app/`)

### 높음: 비밀번호 평문 저장 및 비교

- 위치: [user.py:25,37](../app/api/routers/user.py#L25) 회원가입 및 로그인 처리
- 회원가입 시 `req.password`를 그대로 저장하고 로그인 시 DB 값과 직접 비교합니다.
- DB 또는 백업이 유출되면 사용자 비밀번호가 즉시 노출됩니다.
- 조치: 검증된 비밀번호 해시(예: Argon2id 또는 bcrypt)를 저장하고, 로그인에서 해시 검증 함수를 사용합니다. 기존 사용자 데이터가 있다면 해시 전환 절차도 함께 마련해야 합니다.

### 높음: JWT 기본 비밀키 및 로그 노출

- 위치: [config.py:8](../app/core/config.py#L8), [security.py:14](../app/core/security.py#L14)
- `SECRET_KEY`가 고정된 기본값을 가지므로 설정 누락 시에도 예측 가능한 키로 토큰을 서명합니다. 토큰 생성 함수는 비밀키 자체를 표준 출력에 기록합니다.
- 조치: 키 설정을 필수 환경 설정으로 만들고 안전하지 않은 기본값을 제거합니다. 비밀값 출력은 삭제합니다. 노출된 로그가 있다면 키 교체도 검토해야 합니다.

### 높음: 인증 쿠키의 `Secure` 속성이 항상 꺼져 있음

- 위치: [user.py:38-44](../app/api/routers/user.py#L38) 로그인 쿠키 설정
- `EN_AT` 쿠키에 `secure=False`가 고정되어 있습니다. HTTPS 배포에서도 브라우저가 HTTP 연결로 쿠키를 전송할 수 있습니다.
- 조치: 운영 환경에서 `Secure`를 켜도록 환경 설정을 적용하고, 토큰 만료와 로그아웃 시 쿠키 삭제 정책을 정합니다.

### 중간: 로그인 요청의 DB 세션을 닫지 않음

- 위치: [user.py:33](../app/api/routers/user.py#L33) 로그인 처리
- 로그인 핸들러가 `SessionLocal()`로 세션을 직접 열고 성공·실패 경로 모두 닫지 않습니다. 요청이 누적되면 연결 풀이 고갈될 수 있습니다.
- 조치: 회원가입과 같이 `Depends(get_db)`를 사용해 요청 종료 시 세션을 정리합니다.

### 중간: 이메일 중복 검사가 DB 제약 조건으로 보장되지 않음

- 위치: [user.py:19-28](../app/api/routers/user.py#L19), [user.py:8-11](../app/models/user.py#L8)
- 사전 조회만으로 중복을 막고 사용자 테이블의 이메일 컬럼에 고유 제약이 없습니다. 동시에 들어온 회원가입 요청은 모두 사전 조회를 통과할 수 있습니다.
- 조치: DB 고유 제약을 추가하고 충돌 시 `IntegrityError`를 사용자에게 일관된 오류 응답으로 변환합니다.

### 중간: 게시글 생성 API에 인증·작성자 검증이 없음

- 위치: [board.py:11-19](../app/api/routers/board.py#L11) 게시글 등록 처리
- 로그인 여부나 작성자 식별 없이 게시글을 생성할 수 있습니다. 공개 작성이 의도된 요구사항인지 확인이 필요합니다.
- 조치: 로그인 사용자만 작성할 수 있어야 한다면 인증 의존성과 작성자 연결을 추가합니다. 익명 공개 작성이 의도라면 그 정책을 명시하고 남용 방지책을 검토합니다.

## 프론트엔드 (`frontend/`)

### 중간: 게시글 상세 요청 경합으로 이전 응답이 최신 화면을 덮을 수 있음

- 위치: [BoardDetailView.vue:12-18](../frontend/src/views/BoardDetailView.vue#L12) `load()` 및 경로 변경 감시
- 게시글 ID가 바뀔 때 새 요청을 보내지만 이전 요청을 취소하거나 요청 ID를 확인하지 않습니다. 먼저 보낸 요청이 늦게 끝나면 현재 ID가 아닌 게시글 데이터가 화면에 표시될 수 있습니다.
- 조치: `AbortController`를 사용하거나 요청 식별자를 두어 가장 최근 요청의 응답만 상태에 반영합니다.

### 중간: 글쓰기 폼에서 브라우저 기본 입력 검증이 비활성화됨

- 위치: [BoardCreateView.vue:32-35](../frontend/src/views/BoardCreateView.vue#L32)
- 폼에 `novalidate`가 있고 제목·내용 입력에 `required`가 없습니다. 직접 검사는 공백 입력을 막지만 브라우저의 기본 제약 검증을 끄며, 내용 누락에도 제목 입력으로 포커스가 이동합니다.
- 조치: 네이티브 검증을 사용할지 직접 검증을 유지할지 정하고, 직접 검증을 유지한다면 필드별 오류와 올바른 입력 포커스를 연결합니다.

### 낮음: 로그인과 회원가입의 이메일 정규화가 다름

- 위치: [LoginView.vue:17](../frontend/src/views/LoginView.vue#L17), [SignupView.vue:17](../frontend/src/views/SignupView.vue#L17)
- 회원가입은 이메일 앞뒤 공백을 제거하지만 로그인 요청은 그대로 전송합니다. 사용자가 공백이 포함된 이메일을 입력하면 회원가입 후 로그인이 실패할 수 있습니다.
- 조치: 두 화면에서 같은 이메일 정규화 규칙을 적용합니다.

## 검토 메모 및 범위 제한

- 프로젝트 지침에 기재된 SQLite 파일명은 `app.db`지만 현재 백엔드 기본 설정은 `sqlite:///db.sqlite`이며 저장 위치는 실행 작업 디렉터리에 좌우됩니다. 실행 환경에서 사용하는 파일을 확인하고 설정과 문서를 일치시키는 것이 좋습니다.
- 저장소에서 별도의 OpenAPI/컬렉션 계약 파일은 확인하지 못했습니다. 이 보고서의 API 관련 내용은 라우터 코드 기준 검토이며, 런타임 계약 검증이나 소비자 영향 분석은 포함하지 않습니다.
- `.agents/kakao-login-progress.md`는 별도 Kakao 작업 진행을 설명하지만, 현재 `app/` 검토 범위에서는 해당 OAuth 라우트/어댑터를 확인하지 못했습니다. 따라서 이 보고서는 현재 체크아웃의 코드를 기준으로 하며, 별도 작업 트리의 구현을 포함한다고 보지 않았습니다.
- 프론트엔드 검토에서는 스킵 링크, 주요 랜드마크, 입력 레이블, 오류 알림 등 기본 접근성 지원이 일부 확인되었습니다. 이는 자동 접근성 검사 결과가 아닙니다.

## 권장 우선순위

1. 비밀번호 해시 적용, JWT 키 관리 개선, 민감값 로그 제거
2. 인증 쿠키의 운영 보안 속성 설정
3. 로그인 DB 세션 정리 및 이메일 DB 고유 제약 추가
4. 게시글 작성 정책 확정 후 인증·작성자 검증 적용
5. 상세 화면 요청 경합 및 글쓰기 입력 검증 개선
6. 로그인 이메일 정규화와 SQLite 파일 경로 설정을 일치
